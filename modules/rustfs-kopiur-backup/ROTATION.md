# Credential rotation

This module generates or references four different credentials. They don't rotate the same way -- some are
a single `apply` away, one requires an out-of-band step *before* touching Terraform at all, and two are
entirely outside this module's control. Treat this as the runbook until [#21](https://github.com/isejalabs/terraform-modules/issues/21)
(automated rotation) is decided.

## `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` (the RustFS user)

Safe to rotate in a single `apply`. Replacing `random_password.user_secret` forces `rustfs_user` to be
replaced too (`secret_key` is immutable on that resource), which then flows straight through to an in-place
update of the `AWS_SECRET_ACCESS_KEY` field on the 1Password item -- all in one plan, no manual steps.

```sh
tofu apply -replace='module.bucket_user.random_password.user_secret'
```

The bucket, policy, and quota are untouched; only the user's identity and its 1Password fields change.

## `KOPIA_PASSWORD`

**Not safe to rotate the same way.** This isn't just an access credential -- it's the actual encryption key
kopia used to encrypt the existing repository. Replacing `random_password.kopia_password` in Terraform
*before* re-keying the repository itself will write a new password into 1Password that doesn't match what
the repository was actually encrypted with, locking kopiur out of its own backups.

Correct order:

1. Re-key the kopia repository itself first, out of band (`kopia repository change-password` from a client
   that already has the *current* password), choosing the new password yourself.
2. Only once that's confirmed to have succeeded, bring Terraform's state in line with the new password you
   chose -- via manual state surgery (`state pull` -> patch the `random_password.kopia_password` instance's
   `result` attribute -> `state push`), the same technique used for disaster-recovery imports (see
   `rustfs-bucket-user`'s README). There's no clean `-replace` path here, because Terraform generating its
   own new value and the repository's actual re-keyed value are two independent things that must match
   exactly.
3. `apply` to push the corrected value into the 1Password item.

## 1Password service account token

Not generated by this module -- it's how *Terraform itself* authenticates to write into 1Password, supplied
via `var.onepassword.service_account_token`. Rotating it is entirely manual, outside of any `apply`:

1. Create a new service account token in 1Password's web UI (grant it the same vault access as the one
   it's replacing).
2. Update wherever `var.onepassword.service_account_token` is sourced from (e.g. a SOPS-encrypted secrets
   file) with the new token.
3. Revoke the old token in 1Password once you've confirmed the new one works.

## RustFS admin credentials

Same story as the 1Password token: not generated by this module, supplied via `var.rustfs`. Rotate via
RustFS's own admin interface/API, then update wherever those credentials are sourced from. This module never
stores them.
